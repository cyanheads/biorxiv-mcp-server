### Resources

No standalone resources. All data is reachable through the tool surface and tool-only clients are the primary target.

### Prompts

None. This is a data-retrieval server; no recurring interaction templates are needed.

## Overview

biorxiv-mcp-server exposes bioRxiv and medRxiv preprint data via the Cold Spring Harbor Lab API (`api.biorxiv.org`). It covers ~400K bioRxiv and ~70K medRxiv preprints — life-sciences and clinical research published before, and often months ahead of, journal peer review.

Primary use cases: monitoring new preprints in a field, resolving DOIs to full metadata and revision history, tracking the preprint-to-journal publication crosswalk, and keyword search with relevance ranking (via EuropePMC enrichment). No auth is required. Both servers share one API and are addressed via a `server` parameter; most tools default to querying both.

Pairs naturally with **pubmed-mcp-server** (post-publication side), **openalex-mcp-server** (citation analytics and author disambiguation), and **crossref-mcp-server** (DOI metadata).

## Requirements

- Read-only access to `https://api.biorxiv.org/` — no auth, no write operations
- Polite `User-Agent` header including a mailto address (env var `BIORXIV_MAILTO`)
- Rate limit is undocumented; implement gentle retry with exponential backoff
- Keyword search via EuropePMC (no API key required for basic search) with bioRxiv metadata enrichment — EuropePMC is the relevance engine; the bioRxiv API is the canonical data source
- Category taxonomy is static (hardcoded); 25 bioRxiv and 51 medRxiv categories — the ones the listing endpoint filters on
- DOI is the primary key across all tools
- Pagination via integer cursor (numeric offset) for `biorxiv_list_recent` and `biorxiv_list_published_versions`; offset-based for EuropePMC search results. The API fixes both listing pages — 30 rows on the posting-date listing, 100 on the publication-date listing — and takes no size parameter, so no `limit` is ever sent upstream. `biorxiv_list_published_versions` slices its page locally with `limit` (default 25); `biorxiv_list_recent` takes none.
- Category filtering on `biorxiv_list_recent` is server-side (query parameter `?category=…`, lowercase with `/` and `_` read as a space), not client-side — the API response's `category` field in the `messages` envelope confirms the active filter, and reads `"all"` when the API ignored it.
- Funder filtering on `biorxiv_list_recent` is server-side too (`?funder=<9-character ROR ID>`, sent alongside `category`), bioRxiv only: medRxiv records carry no funder data.

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `BiorxivApiService` | `api.biorxiv.org` — details, publications, pubs (crosswalk by DOI, and by publication-date interval) endpoints | `biorxiv_get_preprint`, `biorxiv_list_recent`, `biorxiv_get_published_version`, `biorxiv_list_published_versions`, `biorxiv_search_preprints` (enrichment), `biorxiv_get_fulltext` (version resolution) |
| `EuropePmcService` | EuropePMC REST API search endpoint — preprint search by keyword and/or author, and abstracts by DOI for records that fall back to EuropePMC metadata | `biorxiv_search_preprints` |
| `BiorxivFullTextService` | `www.biorxiv.org` / `www.medrxiv.org` — rendered full-text HTML article pages (distinct origin from the JSON API); extracts Markdown via the framework HTML extractor | `biorxiv_get_fulltext` |

**BiorxivApiService resilience:**

| Concern | Decision |
|:--------|:---------|
| Retry boundary | Wraps full fetch + parse pipeline; uses `withRetry` |
| Backoff | 500ms base (rate-limit unknown; conservative); 4 attempts (3 retries) |
| Deadline | Every method takes the calling tool's deadline: one 50 s budget per tool call (`CALL_BUDGET_MS`), started once by the handler and shared by every request the call chains. What is left of it is `withRetry`'s `deadlineMs`, bounding every attempt, backoff, and honored `Retry-After`; each attempt runs on the ladder's attempt `signal`, capped at 15 s (details, crosswalk) or 20 s (both listings) or what is left, whichever is shorter. A hung origin settles before a client's 60 s request timeout, as an expiry the calling tool reports under its declared retryable reason |
| HTTP errors | `fetchWithTimeout` throws a status-mapped `McpError` on non-2xx (5xx → `ServiceUnavailable`, 429 → `RateLimited`) |
| Rate limiting | HTTP 429 classified as a retryable `rate_limited` error carrying the parsed `Retry-After` seconds; upstream body never propagated |
| Parse failure | Detects HTML error pages, throws transient not `SerializationError` |

**EuropePmcService resilience:**

| Concern | Decision |
|:--------|:---------|
| Retry boundary | Same `withRetry` wrapper |
| Backoff | 300ms base; EuropePMC recovers quickly from transient errors; 4 attempts (3 retries) |
| Deadline | `search` and `getAbstracts` take the calling tool's deadline the same way, each attempt capped at 20 s or what is left. `biorxiv_search_preprints` runs the search, enrichment, and abstract lookup one after another on one budget, so a late step gets only what the earlier ones left: an expired search fails as `search_unavailable`, an expired enrichment falls back to EuropePMC metadata per record (`enrichment_error: service_error`, `partial_results`), and an expired abstract lookup leaves those records without one, with a notice |
| Result type | Ranked search: `resulttype=lite` (no `abstractText`; EuropePMC ignores a `fields` list, so none is sent). Fallback abstracts: one `resultType=core` query keyed by DOI, page sized to the DOI count |
| HTTP errors | `fetchWithTimeout` throws a status-mapped `McpError` on non-2xx (5xx → `ServiceUnavailable`, 429 → `RateLimited`) |
| Rate limiting | HTTP 429 classified as a retryable `rate_limited` error carrying the parsed `Retry-After` seconds; upstream body never propagated |
| Parse failure | Detects HTML error pages, throws transient not `SerializationError` |

**BiorxivFullTextService resilience:**

| Concern | Decision |
|:--------|:---------|
| Retry boundary | The article-page fetch, inside `withRetry`; a cached extraction makes no request |
| Backoff | 500ms base; 4 attempts (3 retries) |
| Deadline | Takes what version resolution left of the call's budget, each attempt capped at 30 s or what is left; with nothing left, a cached extraction is still served and no request is made. A page that exhausts its attempts or the budget fails `biorxiv_get_fulltext` as the retryable `upstream_unavailable`, with a hint that `biorxiv_get_preprint` still serves the metadata. When resolution used most of the budget and the page was never requested or was still waiting when the budget ran out, that `upstream_unavailable` names the slow lookup instead |
| HTTP errors | 401, 403, 404, 410, and 451 become a `fulltext_unavailable` result, 429 a `rate_limited` one; 5xx, timeouts, and network errors throw |

## Implementation Order

1. **Config** — `src/config/server-config.ts` with Zod schema for all env vars
2. **BiorxivApiService** — details, publications, and pubs (crosswalk) endpoint wrappers with retry
3. **EuropePmcService** — preprint search endpoint wrapper with retry
4. **`biorxiv_list_categories`** — trivial static-data tool; validates service wiring without a live call
5. **`biorxiv_list_recent`** — date-range listing; exercises BiorxivApiService pagination
6. **`biorxiv_get_preprint`** — batch DOI lookup; exercises revision and details endpoints
7. **`biorxiv_get_published_version`** — crosswalk endpoint; fans out across both servers by default
8. **`biorxiv_search_preprints`** — fan-out: EuropePMC search → DOI list → BiorxivApiService enrichment
9. **BiorxivFullTextService** — article-page HTML fetch and Markdown extraction, cached per version; a second origin from the JSON API
10. **`biorxiv_get_fulltext`** — version resolution via BiorxivApiService, then full-text extraction with offset/limit chunking
11. **`biorxiv_list_published_versions`** — publication-date listing over the `/pubs` interval form; reuses the crosswalk record normalization and `biorxiv_list_recent`'s per-server pagination

Each step is independently testable against the live API.

## Domain Mapping

| Noun | Operations | API Endpoint | Notes |
|:-----|:-----------|:-------------|:------|
| Preprint (details) | get by DOI (all revisions) | `/details/{server}/{doi}` | Returns all revisions in `collection[]` in a single call. Fields: `title`, `authors`, `author_corresponding`, `author_corresponding_institution`, `doi`, `date`, `version`, `type`, `license`, `category`, `jatsxml`, `abstract`, `funder` (`"NA"` or an array of `{ name, id, id-type, award }`; `name` and the ROR `id` are misattributed upstream, so only `award` is read), `published` (journal DOI or `"NA"`), `server` (`"bioRxiv"`/`"medRxiv"`; records take the queried server, lowercase, instead). Title, authors, and date are per-revision, but `abstract` is the latest revision's, repeated on every revision, so only the highest version keeps it. Abstracts posted on bioRxiv before December 2019 (numeric DOIs) spell their line breaks as a literal backslash-`n` and carry no real newline. A DOI no server holds answers HTTP 200 with an empty collection. A raw second slash in the key draws an Apache 404 byte-identical to a missing route's (`/detailz/…`), so every slash after the first is sent as `%252F` (the API then answers `DOI not recognizable`, empty) and a 404 always means failure. |
| Preprint (listing) | list by date interval | `/details/{server}/{start}/{end}/{cursor}` | `cursor` is an integer offset (0, 30, 60, …). Always returns exactly 30 results per page. Response `messages[0]` includes `total`, `count_new_papers`, and the active `category` filter value (`"all"` when unfiltered; absent on an empty page). Category is passed as a query parameter in the API's spelling: `?category=hiv%20aids` — a slash, raw or percent-encoded, is ignored. `?funder=` takes only the bare 9-character ROR ID (the URL form draws `status: "funder value must be 9 characters in length"`); an applied filter is echoed as `messages[0].funder: "<name> : https://ror.org/<id>"` (`"all"` when unfiltered), and an ID with no funder record draws `status: "funder value not found"` with no collection. medRxiv answers any funder with `status: "no posts found"`. |
| Published version (crosswalk) | resolve preprint→journal, or journal→preprint | `/pubs/{server}/{doi}`, keyed by the preprint DOI or the journal DOI (matched exactly, case-insensitively) | Returns `preprint_doi`, `published_doi`, `published_journal`, `published_date`, `preprint_title`, `preprint_authors`, `preprint_category`, `preprint_date`, `preprint_abstract`, `preprint_author_corresponding`, `preprint_author_corresponding_institution`. Richer than the `published` field in details. Never parses a `10.64898/` preprint DOI (empty collection, status `no articles found for published version of `); keyed by the journal DOI instead it resolves those. The key is read as its first two `/`-separated segments and a single-encoded `%2F` is a 404, so a journal DOI with a second slash (`10.1093/genetics/…`) sends every slash after the first as `%252F`, which the API decodes back to `/`. |
| Published version (listing) | list by journal publication-date interval | `/pubs/{server}/{start}/{end}/{cursor}` | Same record keys as the DOI form, plus `preprint_platform`; every row carries all twelve, none empty or `"NA"` (552 rows, one week, 2026-10-15). The interval filters on `published_date`; `preprint_date` ranged 2020-01-31..2026-08-25 for the week 2026-09-01..07, with no row posted that week. `cursor` is a plain row offset (cursor 5 returns rows 5–104), 100 rows a page, in a stable but unsorted order. `messages[0]` carries `total` as a string (`"449"`) and echoes `cursor` as a number at 0 and a string after it. An empty interval, an inverted one, and a cursor at or past the last row all answer HTTP 200 with `status: "no articles found for <start> <end>"` and no `total`; a malformed date draws `"Both dates must be in yyyy-mm-dd format"`, and `both` or a capitalized server draws `"Server not recognized"`. `?category=` is ignored. `10.64898/` rows list normally. |
| Published version (listing by publisher) | list bioRxiv's rows by journal DOI prefix and publication-date interval | `/publisher/{prefix}/{start}/{end}/{cursor}` (no server segment, no `/json`) | bioRxiv only: `?server=medrxiv` is ignored (byte-identical answer) and `/publisher/medrxiv/…` is an Apache 404; medRxiv's six `10.1016/` rows for 2026-10-01..02 never appear. Rows carry six keys — `biorxiv_doi`, `published_doi`, `preprint_title`, `preprint_category`, `preprint_date`, `published_date` — and no journal name, authors, corresponding author, or abstract. The row set equals the bioRxiv `/pubs` rows whose `published_doi` starts with the prefix (2026-10-01..02: `10.7554` 5 of 5, `10.1016` 19 of 19). Paging matches `/pubs`: 100 rows a page, `total` as a number (`401`), `cursor` echoed as a string after 0, and `status: "no articles found"` with no total for an empty interval, a prefix with no rows (`10.9999`), or a cursor past the end. A prefix it cannot read (`10.755`, `10.1`, `abc`) answers HTTP 200 with `status: "publisher string not recognized"` and no rows (checked 2026-10-23). |
| Categories | list | Hardcoded taxonomy (static) | No API endpoint; static list maintained in code. |
| EuropePMC search | full-text search returning DOIs | `GET /search?query=…&resulttype=lite&filter=preprint` | Returns ranked DOIs used to drive enrichment via details endpoint. Lite records carry `doi`, `title`, `authorString`, and `firstPublicationDate`, never `abstractText`. |
| EuropePMC abstracts | abstracts by DOI | `GET /search?query=(DOI:"…" OR DOI:"…") AND SRC:PPR&resultType=core&pageSize=<n>` | Only for records that fell back to EuropePMC metadata when abstracts are requested. `core` records carry `abstractText` (3.5–4.3 KB a record measured, against 0.7 KB for lite). One query answers up to the tool's 100-result limit: 100 DOIs returned 100 records, each with an abstract, on one page (checked 2026-09-22). |

The bioRxiv API uses `{server}` as either `biorxiv` or `medrxiv`; no multi-server single call exists. Fan-out to both servers happens in the tool handlers: listings keep each server's page and pagination state separate rather than merging them (`Promise.allSettled`), and DOI lookups name the server that answered. A two-server lookup of one DOI — each DOI in `biorxiv_get_preprint`, the resolution steps of `biorxiv_get_fulltext` and `biorxiv_get_published_version`, and search enrichment of a DOI with neither preprint prefix — ends the moment the server holding the DOI answers, since the other server's answer cannot change the result.

**`biorxiv_list_recent` pagination with `server="both"`:** when fanning out across both servers, each server has its own independent `total` and `cursor`. The response must surface per-server pagination state (e.g., `{ biorxiv: { cursor: 30, total: 550 }, medrxiv: { cursor: 30, total: 210 } }`) so callers know how to advance each server's cursor independently. A single merged `cursor` number is ambiguous and wrong here.

Because the two servers hold different result counts for the same interval, one cursor can be valid for one server and past the end for the other. The API answers an out-of-range cursor with an empty collection and `total: 0`, which would otherwise read as "this server has nothing in the interval". Each per-server entry therefore carries an `exhausted` flag (`true` when zero records came back at a non-zero cursor); `total` stays present and required, and a `notice` names the exhausted server when the other still returned records.

A server that never answered is the other half of that problem and is kept distinct from it. It has no cursor and no total, so it gets no `pagination` entry at all — and an omitted entry is invisible, leaving a partial result indistinguishable from a complete one. It is therefore reported in a top-level `failed[]` (`{ server, error }`), rendered as its own line in the per-server summary, and named in the `notice`. `exhausted` stays reserved for a server that answered; `failed[]` for one that did not. The call still returns the surviving server's page — a partial result beats none, provided the caller is told it is partial and at least one server answered. Because `ctx.enrich.notice` is last-wins, every qualification that applies (failed servers, exhausted cursors, zero results) is composed into a single notice string with the partial-result sentence first, since it changes how every other number in the response reads.

**`biorxiv_list_published_versions` takes the same shape with three upstream differences.** Upstream pages hold 100 rows, of which each server serves the first `limit` (default 25); one week's totals were bioRxiv 449 and medRxiv 103, so at cursor 200 medRxiv is exhausted while bioRxiv has 249 rows left. Past the end, the API reports no `total` at all rather than `total: 0`, so an exhausted entry carries `cursor` and `exhausted: true` and no `total`; an empty page at cursor 0 is an empty interval and reports `total: 0`. `nextCursor` is the cursor plus the upstream rows served, so a walk at any `limit`, started at any offset, reaches every row once; a cursor that is not a multiple of 100 is a plain offset upstream (cursor 37 returns rows 37–136). Whenever a server has a `nextCursor`, the enrichment `truncated`/`shown`/`cap` fields are set (`cap` is the per-server page size times the servers queried, the most `shown` can reach) and the notice names the servers with rows left. Under `"both"`, when only one server still has rows and neither failed, the notice says to pass that server as `server`: a caller that kept `"both"` would re-request the finished server on every later page. Its single-server failure takes the same retryable `upstream_unavailable` / `rate_limited` contract as a two-server one, instead of bubbling the service's own error.

When *no* attempted server answered there is nothing left to qualify, and the call raises a retryable error instead of returning a page. "Nothing found here" is a claim about what the servers reported and none of them reported, so an empty success would be indistinguishable from an interval that genuinely holds nothing — for any caller that branches on success-vs-error rather than reading prose. This is the same rule `biorxiv_get_preprint` applies to a DOI whose every server failed, and `failed[]` therefore never holds the full server set.

A cancelled call is never a partial result. Once the caller's `ctx.signal` has fired, every fan-out handler rethrows the cancellation (`ctx.signal.throwIfAborted()` after each fan-out, and before returning an article the cache answered) instead of naming the aborted leg in `failed[]`, degrading to a notice, or returning the leg that finished first, so the call is recorded as `RequestCancelled` (-32011). The SDK writes no response to a cancelled request either way; the check keeps the server's own record of the call honest. A leg the call's deadline stopped is an upstream failure, not a cancellation — the deadline never aborts `ctx.signal`.

## Workflow Analysis

### `biorxiv_search_preprints` (fan-out workflow)

| # | Call | Purpose |
|:--|:-----|:--------|
| 1 | `EuropePmcService.search(query, filter=preprint)` | Ranked DOI list with titles |
| 2a | `BiorxivApiService.getDetails(doi, "biorxiv")` ×N | Enrich matching DOIs on bioRxiv — one call per DOI returns all revisions |
| 2b | `BiorxivApiService.getDetails(doi, "medrxiv")` ×N | Enrich matching DOIs on medRxiv — under `server=both`, after bioRxiv answers empty, or alongside 2a for a DOI with neither preprint prefix |
| — | Merge by DOI, surface `server` field on each result | Deduplication |
| 3 | `EuropePmcService.getAbstracts(fallbackDois)` ×1 | Abstracts for records that fell back to EuropePMC metadata — only when `include_abstract` is true and at least one record fell back |

The DOIs are enriched in parallel. Under `server="both"`, a DOI's prefix is a hint, not the server: both servers issue `10.1101/` and `10.64898/` DOIs, so such a DOI runs 2a and then 2b only when bioRxiv answers empty — a second request only for a medRxiv preprint. A DOI with neither prefix runs 2a and 2b in parallel through `firstHit`, settling on the server that holds it. Enrichment failures degrade to EuropePMC-only metadata for that record, surfaced in a `partial_results` flag. Step 3 degrades the same way: a failed lookup leaves those records without an abstract, and the notice says so. Step 1 has no such fallback — a failure there ends the call, as `search_unavailable` or, for an origin 429, `rate_limited`.

### `biorxiv_get_preprint` (batch lookup)

`/details/{server}/{doi}` returns **all revisions** in a single `collection[]` response. No revision enumeration loop is needed.

| # | Call | Purpose |
|:--|:-----|:--------|
| 0 | `normalizeDoi(entry)` for every entry, in input order | An unparseable entry goes to `failed[]` as `invalid_doi_format`; a repeat of a bare DOI already seen is dropped; the first 10 distinct DOIs go on to step 1 and the rest to `unprocessed[]` |
| 1 | `BiorxivApiService.getDetails(doi, server)` for each of those DOIs × each server | One call per (DOI, server) pair, all in parallel under the call's one deadline; each call returns all revisions for that preprint |
| — | Assemble `preprints[]`, `failed[]`, and `unprocessed[]` in input order; surface `server` field; report per-DOI failures in `failed[]` | Partial success |

When `server="both"`, each DOI generates two calls (biorxiv + medrxiv) run in parallel through `firstHit`: the DOI settles the moment the server holding it returns revisions and the other call is aborted, so a stalled server that does not hold it never holds up a DOI the other server found. A DOI neither server returned waits for both answers, and its `failed[]` classification reads them all. When `server` is specified, one call per DOI. Partial success reported per-DOI in `failed[]`. Note: if a DOI exists only on bioRxiv, the medrxiv call returns an empty collection (not an error) — this is not a failure.

**Ten lookups a call, the rest returned.** A read with a cap processes up to it and names the remainder instead of rejecting the call. The cap stays 10: at 10 DOIs a call already sends 20 concurrent `/details` requests under `"both"` (80 when the origin fails and every ladder retries) to an origin shared by every user of the hosted endpoint, and a 10-DOI reply measured 35.5 KB of `content[]`. The schema ceiling is 200 entries, the largest page any other tool here returns (`biorxiv_list_published_versions` under `"both"`), so a page of DOIs passes whole. `unprocessed[]` holds bare, valid, distinct DOIs in input order and can be sent back as `dois` unchanged; an enrichment notice names the cap, and counts the retryable `failed[]` entries to include in a later call, which the remainder alone would never retry. The remainder is never fetched inside the call — a loop over chunks would multiply wall time under the one 50 s budget. Normalizing before the cap keeps an invalid entry (free to classify) and a repeat (two requests for an identical entry) from taking a place.

"Not found" is a claim about what the servers reported, so it requires every attempted server to have answered. A DOI whose lookup failed on any server it needed — the call's deadline stopping it included — is classified `upstream_unavailable` (retryable), not `not_found` — on the per-DOI `failed[]` entry and, when nothing in the batch resolved and `unprocessed[]` is empty, on the thrown error. A batch-level error speaks for every requested DOI, so a remainder that was never looked up rules it out: that call returns its `failed[]` entries and `unprocessed[]` instead. The same rule governs the single-server path, where one failed call leaves absence equally unestablished.

## Known Limitations

- **bioRxiv native search is not used** — the `/search` endpoint is weak and undocumented. EuropePMC provides relevance-ranked results but may lag new preprints by 1–2 days.
- **Full-text via HTML extraction (best-effort, not JATS)** — `biorxiv_get_fulltext` retrieves full text by fetching the rendered HTML article page (`www.{server}.org/content/{doi}v{N}.full`) and extracting Markdown via the framework HTML extractor. There is no keyless JATS source: the `.full.xml` suffix falls back to HTML, and JATS proper is S3-TDM/requester-pays only. Section structure is therefore approximate, not structured JATS. Coverage is partial — some preprints are PDF-only (empty extraction) and some origins may block programmatic access (Cloudflare); both surface as a typed `fulltext_unavailable` error routing to `biorxiv_get_preprint`, while an origin rate limit (429) surfaces as a retryable `rate_limited` error. Long articles page via offset/limit character chunking. Table cells are never on the article page — Highwire serves each table from a separate expansion page on the same rate-limited origin — so a table reaches the text as its caption alone, and `omittedTables` names it with that page's URL.
- **Posting-date listing page size is fixed at 30** — the API does not accept a `limit` parameter; `biorxiv_list_recent` pages by stepping the cursor offset (0, 30, 60, …). The `total` field in the response lets clients calculate total pages. The publication-date listing's upstream page is fixed at 100 rows (next entry).
- **Publication-date listing: a 100-row upstream page, one bioRxiv-only filter, and a total that can grow** — the `/pubs` interval form serves 100 rows a page whatever the caller wants, so `biorxiv_list_published_versions` slices it locally, and a walk at a small `limit` repeats upstream requests: one server's week (449 rows) takes 18 requests at `limit` 25 against 5 at 100, each fetching up to 100 rows with abstracts. Nothing is cached between calls. The form ignores `?category=`, so the tool offers no category filter. The publisher filter reads the separate `/publisher` listing, which exists for bioRxiv only and narrows by a whole DOI prefix (`10.1016` is all of Elsevier, not one journal), with rows that omit the journal name, authors, and abstract. A past interval's total can rise as later matches are recorded (the week 2026-09-01..07 was cited as 444 on 2026-09-30 and measured 449 on 2026-10-15), so a walk spread over days can skip or repeat rows if new ones land mid-order; a walk inside one session read 449 unique DOIs.
- **medRxiv lists some `10.64898/` preprints twice** — its `/pubs` rows can repeat one preprint and journal DOI with different `preprint_date` values, and sometimes a different title or author list: the week 2026-09-01..07 held 103 rows for 100 preprints (rows 2/3, 4/5, and 18/19 of its first page, rechecked 2026-10-17), and the journal-DOI crosswalk and `/details` return the same pairs, `/details` as two `version: "1"` entries. Every upstream row is kept — collapsing them would break the cursor arithmetic, which counts upstream rows — so a walk reaches each row once, not each preprint once, and `preprintDate` is the date a row records, the first posting for most preprints but not for these. `biorxiv_get_published_version` returns the first record listed.
- **Category filter on listing is server-side** — the API filters by category, but answers a category it does not recognize with its unfiltered listing and a `messages[0].category` of `"all"`, never an error. The taxonomy is validated before the call, and the echo is checked after it: a leg whose filter was ignored is dropped with a notice, and a call left with no filtered page raises `invalid_category`.
- **Record-level funder names are unusable** — every funder entry's `name` and ROR `id` name an unrelated organization (mostly hospitals) while the `award` stays the real grant number, so records expose `awards` only. Awards are kept verbatim: upstream runs several grants together without a separator (`R35GM134936R01CA260414K99GM155323`) and nothing marks the boundaries, and a few carry HTML entities (`DE&#8208;SC0023160`) or upstream backslashes (`RP\_018\_20230628`) as sent.
- **The funder filter's registry is upstream's, and it moves** — which ROR IDs `api.biorxiv.org` holds a funder record for is not published. NIH (`01cwqze88`) answered `"funder value not found"` for every probed window on 2026-09-22 and resolved (70 August 2026 preprints) about an hour later. `invalid_funder` for an unknown ID is therefore a statement about the registry at call time.
- **No multi-server batch endpoint** — the API requires separate calls per server; the tool handlers fan out via `Promise.allSettled`, or `firstHit` for a lookup of one DOI.
- **Rate limits undocumented, and every origin enforces one** — neither `api.biorxiv.org`, the `www.{server}.org` article pages, nor EuropePMC publishes a quota, and all three answer HTTP 429 once tripped. The article pages sit behind a Cloudflare edge that starts limiting after a handful of consecutive fetches. A `Retry-After` is read when the response carries one, and every hint falls back to generic wording when it does not — or when it names no positive wait (`0`, an HTTP-date already past), since a "wait 0 seconds" hint sends the caller straight back into the limiter. Each is classified as a retryable `rate_limited` error carrying the parsed wait — `BiorxivFullTextService` for the article pages, `BiorxivApiService` for the JSON API, `EuropePmcService` for search — and `biorxiv_get_fulltext`'s per-version extraction cache removes the repeat article-page fetches that provoked its side. `withRetry` honors a positive `Retry-After` and fails fast when the requested wait exceeds its 30s cap or what is left of the call's budget; the one local step is `retryWithinBudget` keeping a `Retry-After` that names no positive wait from it, so that 429 takes the exponential backoff a header-less one does instead of an immediate re-send. No other backoff layer belongs here.
- **Category list is hardcoded** — no API endpoint provides the taxonomy; the static list may drift as new categories are added.
- **`format()` must be content-complete** — Claude Desktop reads `content[]` from `format()`, not `structuredContent`. Every tool's `format()` function must render all fields the LLM needs (revisions, published DOI, category, abstract whenever the record carries one, pagination state) in markdown, not just a count or title. `include_abstract` decides whether a listing or search record carries an abstract at all, and it removes the field from both surfaces together. This is particularly important for `biorxiv_get_preprint` where the revision list and crosswalk data are the primary output.
- **Some upstream glyphs are lost before they reach the server** — the Highwire export writes symbols as placeholders, and a few carry less than the source had. A `*` may be a lost `•` (bioRxiv has `A*T to G*C` where EuropePMC has `A•T to G•C`), `{superscript 1}3C` is ¹³C with the second superscript gone, and `{square}` and `[Formula]` stand for characters the export dropped. `normalizeUpstreamText` maps each placeholder to what its name says and cannot restore what it never names. Single-letter brackets (`[A]` for Å, `[a]` for α) stay verbatim because the same form is concentration and set notation elsewhere.
- **Heading detection reads a closed list at the start of a paragraph** — a heading outside the list, or one not opening its paragraph (`(1) BackgroundMany …`), stays fused. A paragraph that opens with a CamelCase name or an acronym starting with a listed heading (`DesignMaster …`, `AIMP1 …`) would be split; none of the 7,770 sampled records has one, and single-line text such as a title is never split.
- **`content[]` carries a few Markdown escapes** — upstream text is escaped only where a character would otherwise change rendering, so an agent reading the raw `content[]` text sees `A\*T`, `\<COMP id>`, and `(\~10 lux)` but `p<0.05`, `cc_by`, and `[95% CI …]` as sent. Across the 5,788-record sample that is 261 backslashes, 60 of them for `*`. A span copied out of `content[]` can still carry one; `structuredContent` carries the unescaped text.

## Decisions Log

### Answered questions

- **Search relevance: EuropePMC fallback or date-range only?** → EuropePMC fallback implemented as `biorxiv_search_preprints`. Rationale: date-range browsing alone forces the agent to read hundreds of entries to find relevant work; relevance search is the primary discovery workflow and EuropePMC indexes bioRxiv/medRxiv reliably.
- **Full-text retrieval: in scope?** → Deferred. `biorxiv_get_preprint` returns the PDF URL and abstract; parsing PDF/TDM XML is a separate concern with significant complexity and no clear agent workflow that requires it vs. using the URL directly.
- **Category taxonomy: hardcode or fetch dynamically?** → Hardcoded static list. No API endpoint provides it; the taxonomy changes infrequently; a dedicated `biorxiv_list_categories` tool exposes it so agents can discover valid values without baking category strings into tool parameters.
- **Two-server fan-out: default scope?** → Default to both servers (`"both"`) with optional `server` parameter to scope down. Rationale: agents asking about a topic don't typically want to miss medRxiv results when asking about bioRxiv and vice versa.

### Options declined

- **`biorxiv_search_preprints` using the native `/search` endpoint** → Declined; the endpoint is sparsely documented and returns poor relevance ordering. EuropePMC provides significantly better recall and ranking for preprint search.
- **Separate `biorxiv_get_revisions` tool** → Declined; revision history is included in `biorxiv_get_preprint` output. A separate tool adds surface area without enabling a workflow that `get_preprint` doesn't already cover.
- **Resources exposing preprints by DOI** → Declined; most clients are tool-only, and `biorxiv_get_preprint` already provides the same data. Adding resources would create a second surface with no coverage gain.
- **Prompts for literature review workflows** → Declined; this is a data retrieval server. Prompt templates add maintenance cost without meaningfully improving agent behavior — the tool descriptions carry sufficient operational guidance.
- **Wrapping EuropePMC search behind a facade that hides it as the backend** → Declined in favor of transparency: `biorxiv_search_preprints` is the tool name (user-facing intent), but the Known Limitations section documents that EuropePMC powers it, so maintainers understand the dependency. No implementation detail leaks into tool descriptions.
- **Full-text retrieval via TDM API** → Deferred (not declined permanently). The TDM endpoint requires a separate agreement for bulk access; for targeted agent use, returning the PDF URL and abstract covers the common case. Can be added as `biorxiv_fetch_fulltext` in a future iteration.

### Post-review corrections (API verification)

- **`cursor` type corrected: `string` → `number`** — Live API probe confirms the cursor is a plain integer offset (0, 30, 60, …), not an opaque string token. The `cursor` field in the response envelope also returns as an integer. Removing the `limit` parameter from `biorxiv_list_recent`: the API page size is fixed at 30 regardless of any `limit` param; exposing a `limit` input would create false expectations.
- **Category filtering is server-side, not client-side** — The listing endpoint accepts `?category=neuroscience` as a native query parameter and confirms the active filter in `messages[0].category`. The design erroneously implied client-side filtering. This is a meaningful efficiency win: no need to over-fetch and discard.
- **`/details/{server}/{doi}` returns all revisions in one call** — Confirmed via API probe: a DOI with 3 revisions returns all 3 in `collection[]` from a single call. The Workflow Analysis for `biorxiv_get_preprint` previously implied a per-revision enumeration pattern; that was wrong and has been corrected.
- **`biorxiv_get_published_version` scope narrowed** — `biorxiv_get_preprint` already surfaces the journal DOI in the `published` field. `biorxiv_get_published_version` (using `/pubs/{server}/{doi}`) provides richer crosswalk metadata (journal name, published date, corresponding author institution). Retaining the tool but narrowing its described use case to when the richer crosswalk fields are needed — not as the primary DOI resolution path.
- **`biorxiv_search_preprints`: `category` filter removed** — EuropePMC's preprint search does not support server-side category filtering in the same taxonomy as bioRxiv. Dropped `category` from this tool's inputs to avoid a false client-side filter that would silently degrade to no-op; agents that want category-scoped results should use `biorxiv_list_recent` with `category`.
- **Error contracts added** — No error contracts were declared in the original design. Added a typed error contract table for all five tools covering the domain failure modes an agent should plan around (DOI not found, invalid date range, invalid category, EuropePMC unavailable, crosswalk not found).

### Full-text retrieval — now implemented (`biorxiv_get_fulltext`)

Previously deferred (see the "Deferred" notes above); implemented after an API design pass.

- **Source: rendered HTML page, not JATS.** Verified there is no keyless JATS source — `…v{N}.full.xml` falls back to HTML, and JATS proper is S3-TDM/requester-pays only. So the tool fetches the `.full` HTML page and extracts Markdown via the framework `htmlExtractor` (`defuddle` + `linkedom`, added as direct deps). Honest `contentFormat: 'html-markdown'` label plus a best-effort caveat; section structure is not guaranteed.
- **Content selector `.fulltext-view`.** bioRxiv/medRxiv render on the Highwire platform; defuddle's auto-detection latches onto the reference apparatus and misses the body (~383 words vs ~10,197 for one probed article). Passing the `.fulltext-view` selector captures the full text; defuddle falls back to auto-detection when the selector misses, so it is always safe to pass.
- **Distinct fetch path from the JSON API.** The full-text fetch EXPECTS `text/html`, so it does not route through `BiorxivApiService`'s "HTML response = upstream error" guard. It lives in a separate `BiorxivFullTextService` with its own per-server web-host config (`BIORXIV_WEB_BASE_URL` / `MEDRXIV_WEB_BASE_URL`).
- **Coverage handled as typed errors, not crashes.** PDF-only preprints (empty extraction), Cloudflare block/challenge pages, and 403/404 responses map to one `fulltext_unavailable` reason routing to `biorxiv_get_preprint`; a page that stays unanswered through transient 5xx/timeouts or runs out the call's budget fails as the retryable `upstream_unavailable`. Challenge/interstitial pages are detected and never fed to the extractor.
- **Chunking mirrors `gutenberg_get_text`.** offset/limit character chunking with `totalChars`/`remainingChars`/`hasMore` disclosure so long articles are fully readable across calls.
- **Extracted articles cached in `ctx.state` under `fulltext/v5/{server}/{doi}/{version}`, TTL one hour.** The `v5` segment is the cached-value generation, bumped whenever the cached shape or its Markdown changes. Paging previously cost a full origin fetch plus a full Defuddle extraction per chunk, which is what tripped the origin's rate limiter partway through long articles. The key is slash-delimited because the storage layer validates keys against `[a-zA-Z0-9_.\-/]` and rejects a colon separator outright. The cache is tenant-scoped (`ctx.state`), never process-wide, and only `kind: 'article'` results are written — a blocked, rate-limited, or empty page must be able to recover on a later call. It is an optimization and never a dependency: a storage backend that refuses the read or the write degrades to an origin fetch rather than failing the request, and a tenant-less caller (HTTP + JWT with no `tid` claim) runs uncached. TTL is a constant rather than an env var: nothing has asked to tune it, and a knob would need declaring across `.env.example`, `server.json`, `manifest.json`, and the README.
- **HTTP 429 classified as its own `rate_limited` reason.** 429 does not belong in `DETERMINISTIC_UNAVAILABLE_STATUSES` — that set means "a re-fetch will never succeed", and a rate limit is the opposite. The retry side is already handled by the framework: `withRetry` honors `data.retryAfter` and fails fast when the requested wait exceeds `maxDelayMs` (30s), so no local backoff logic is needed. What the tool adds is a typed retryable reason carrying the parsed `Retry-After` and a recovery hint naming `biorxiv_get_preprint`. The error payload carries only the parsed wait — the origin's block-page HTML (`data.body` / `data.responseBody`) is deliberately not propagated.
- **DOI resolution defaults to `server="both"`.** Both servers issue `10.1101/` DOIs, so a caller holding a bare DOI cannot tell which value to pass and a medRxiv preprint missed at the `biorxiv` default. Resolution fans out across both and settles on the first server to return revisions, aborting the other lookup (see *One time budget per tool call*); two answers in the same tick go to bioRxiv. The full-text fetch stays single-server against the one that answered, and the output `server` field keeps its two-value enum. An all-rejected fan-out raises the retryable `upstream_unavailable` rather than collapsing into `doi_not_found`.
- **`biorxiv_get_usage` descoped.** The same design pass proposed a per-preprint usage/metrics tool; bioRxiv's `/usage/{m|y}/{cursor}` endpoint returns corpus-wide aggregate stats, not per-preprint counts, so it cannot back that tool. Not built.

### `author` filter on `biorxiv_search_preprints`

- **Author maps to an EuropePMC `AUTH:"…"` field query,** ANDed with the keyword query in `EuropePmcService`. `query` was relaxed to optional with a schema refine requiring at least one of `query`/`author`, so author-only search is valid and existing query-only calls stay valid. Embedded double-quotes are stripped from the author value so a stray quote cannot break the AUTH phrase.

### Rate limiting on the JSON API, and total-failure classification

- **`BiorxivApiService` classifies HTTP 429 the same way `BiorxivFullTextService` does.** The JSON API origin rate-limits too, and previously a 429 reached the caller as a bare `RateLimited` with no `reason`, no recovery hint, and — because `fetchWithTimeout` attaches it — the upstream response body. The service now rebuilds the payload from scratch: `{ reason: 'rate_limited', retryable: true, retryAfter?, recovery }` and nothing else. The full-text service's `kind: 'unavailable'` result shape was deliberately *not* mirrored here: that shape exists because a blocked article page has a graceful-degradation branch to route to, and the metadata path has no partial preprint to fall back on, so throwing is the honest outcome. No retry logic was added — `withRetry` already honors `Retry-After` and fails fast past its cap, so classification and payload hygiene were the whole gap.
- **`parseRetryAfterSeconds` moved to `services/shared.ts`.** Both fetch paths read the same header in the same two RFC 9110 forms; a second copy would be a second thing to get wrong. It joins `detectHtmlError` and `normalizeUpstreamText`, alongside a new `findRateLimit`, which reduces a set of rejections to the wait a caller should honor — the *longest* of the reported ones, since a shorter wait would still land inside whichever origin asked for the longer one.
- **A rate limit outranks a generic upstream failure wherever both can contribute.** When a tool's every-attempt-failed branch mixes a 429 with an unrelated outage, it raises `rate_limited` rather than `upstream_unavailable`. Both tell the caller to retry, but only one says when, and retrying sooner than the origin asked would land straight back inside the same limit — so the more specific reason is also the safer one. The generic reason stays for the case where no 429 was involved at all.
- **`biorxiv_get_fulltext` keeps one `rate_limited` reason for two origins.** Its version resolution hits `api.biorxiv.org` while its full-text fetch hits the article page, and either can 429. A second reason was rejected: from the caller's seat both mean "wait the stated interval, then retry", so the branch would have no distinct action behind it. What genuinely differs is the fallback advice — `biorxiv_get_preprint` shares the metadata origin, so recommending it while *that* origin is the limited one sends the caller back into the limit. The recovery hint therefore names the limiting origins and adapts the fallback, and the two payloads stay structurally distinct anyway (`sourceUrl` on the article-page case, `servers` on the resolution case). Both can be limiting at once: under `server="both"` one server answering resolution says nothing about whether the metadata origin let the other one through, so an article-page limit re-reads the resolution rejections before claiming the fallback still works, and the reported wait is the longer of the two — a retry re-runs resolution as well as the fetch.
- **`biorxiv_list_recent` raises on total failure instead of returning an empty page.** One server failing under `server="both"` still returns the other's page — that is the partial-result case and it is unchanged. Every attempted server failing is a different condition: the tool used to return a successful empty listing with a notice explaining that nothing answered, which a caller branching on success-vs-error could not tell from an empty date interval without parsing prose. It now raises the retryable `upstream_unavailable` (or `rate_limited`) that `biorxiv_get_preprint` already raised for the equivalent DOI case, which also makes `failed[]` structurally incapable of holding every attempted server. A single-leg call — an explicit server, or `"both"` narrowed by a funder filter or a server-exclusive category — takes the same contract rather than bubbling the service's own error, which reached the caller with no declared reason (a budget expiry as a bare `Timeout`).
- **`biorxiv_search_preprints` enrichment carries every latest-revision field.** `type`, `license`, `funder`, and `authorCorrespondingInstitution` were absent from the enriched projection, so the same DOI described less through search than through `biorxiv_get_preprint` even when the upstream record carried all four. They now ride the enriched branch, the output schema, and `format()` (`funder` has since given way to `awards` — see *Funder metadata* below) — the last of those is what keeps `content[]`-only clients level with `structuredContent` ones. Full revision *history* stays out of search: `revisionCount` plus `biorxiv_get_preprint` remains the detailed-history workflow.
- **An enrichment 429 degrades rather than failing the search; a search 429 raises.** The split follows what each path has to fall back on. Every enrichment failure falls back to EuropePMC metadata, and a rate limit is no more fatal there than a 5xx, so it only gets its own `enrichment_error: 'rate_limited'` value — enough for a caller to tell "wait, then retry" from "this DOI is not indexed on the target server". The EuropePMC search is the tool's primary call and has nothing to degrade to, so a 429 there raises the `rate_limited` contract entry. The two live in separate `catch` blocks — the search's own `try` and the per-DOI enrichment `try` inside the result map — so neither branch can capture the other's rejections.
- **`EuropePmcService` classifies HTTP 429 the way `BiorxivApiService` does.** Both throw; `BiorxivFullTextService` recognises a 429 too but returns a `kind: 'unavailable'` result, because its article-page fetch has a degrade path neither of the other two has. Before this, a EuropePMC rate limit reached `biorxiv_search_preprints` as `search_unavailable` — the reason declared for "unreachable or a server error", which a 429 is neither — and the origin's `Retry-After` was dropped on the way out, so a caller was told to retry "after a short delay" when the origin had named a wait. The service now rebuilds the payload from scratch: `{ reason: 'rate_limited', retryable: true, retryAfter?, recovery }` and nothing else, so the upstream response body `fetchWithTimeout` attaches never crosses into it. No retry logic was added — `withRetry` already honors `Retry-After` and fails fast past its cap.
- **The search rate-limit hint routes to `biorxiv_list_recent`, and says only that the limit does not cover it.** EuropePMC is the only origin `biorxiv_search_preprints` reaches for search, and naming that origin's own endpoint as the fallback would send the caller straight back into the limit. `biorxiv_list_recent` reads `api.biorxiv.org`, which an EuropePMC limit does not extend to — but the search is step 1, so nothing in the call establishes whether that origin is answering, and `api.biorxiv.org` rate-limits independently. The hint therefore states the scope of the limit and offers the listing to try, never that it will answer. Compare `biorxiv_get_fulltext`, which does have resolution rejections to read and so can claim the metadata origin still works.

### EuropePMC empty-body responses, and `wordCount` from the served text

- **A 200 body with no `resultList` is retried, never read as zero matches.** EuropePMC sometimes answers with only `{"version":"6.9"}`: about one request in five for a valid first page, about one in eight for a valid cursor page, and, before EuropePMC began answering one with HTTP 503, every time for a malformed `cursorMark`. A genuine zero-hit answer still carries an empty `resultList`, so a missing one is unambiguous. `EuropePmcService` throws it as a transient `ServiceUnavailable` inside `withRetry`, so the intermittent case clears transparently (four attempts).
- **A cursor past the last match is the end of the list, not a failed search.** EuropePMC still returns a `nextCursorMark` on the page holding the last match, and the page after it comes back with an empty `resultList` and the query's real `hitCount`. With a supplied cursor and a non-zero `hitCount`, the notice says every match was on earlier pages rather than suggesting broader search terms.
- **A cursor page that fails the way a malformed token does is checked against the query's first page.** EuropePMC answers a `cursorMark` it does not recognize on every attempt with HTTP 503 and its generic "temporarily unavailable" body (earlier, with the empty body), so neither status nor body separates a bad token from an outage. With a `cursor_mark` other than `*`, a ladder that every attempt failed with a 503 or the empty body sends one more request, unretried: the same query at `cursorMark=*`, `pageSize=1`, timed out at 20 s or what is left of the call's budget, skipped when nothing is, on the caller's signal. A 200 carrying a `resultList` raises `invalid_cursor_mark`, a `ValidationError` whose hint says to reuse the prior page's `nextCursorMark` or restart from `*`; anything else keeps the ladder's failure, `search_unavailable`. One attempt is enough: a miss errs toward the retryable reason, and a second ladder would only add requests against an origin that may be down. The cursor branch spends the full retry budget first: a valid cursor draws a transient 503 or empty body too, so a shorter ladder would mislabel it as invalid. A malformed cursor costs five requests plus about two seconds of backoff before the error. A first page never sends the extra request and raises `search_unavailable`, whose hint does not mention `*`, because the request already started there. Neither does a ladder in which any attempt drew a 429, another 5xx, or a network failure, even one that ended on a 503, nor a ladder the call's budget cuts short, which ends as an expiry, `search_unavailable`: the attempts that did not run might have answered.
- **The service writes the empty-body error messages itself.** `withRetry` appends `(failed after N attempts)` to an exhausted error. The service rebuilds both errors with their own wording and puts the count in `data.retryAttempts`. The tool branches on `data.reason`, never on message text.
- **`biorxiv_get_fulltext` counts `wordCount` from the Markdown it pages over.** defuddle's `wordCount` counts the text nodes of its intermediate HTML, before Markdown serialization. It never sees heading and list markers, link targets, or image alt text, so it is not a measure of `content`. The tool now counts whitespace-delimited tokens of the same string `totalChars` measures, and the field is always present. The service no longer carries a word count, and the cache key moved to `fulltext/v2` so entries holding the extractor's figure are never read back.

### Category spelling, the `10.64898/` crosswalk, and DOI input forms

- **Categories are sent in the API's spelling: lowercase, `/` and `_` read as a space.** A live sweep of every taxonomy entry found `HIV/AIDS` ignored in any form containing a slash (raw or `%2F`) and filtered as `hiv aids`. The same spelling is what every record's `category` field carries, so it doubles as the input match key: `Cell Biology`, `cell biology`, and `cell_biology` are one filter, and a category copied off a result works as input. `-` is read as a space in input too, so the websites' collection slugs (`cell-biology`, `hiv-aids`) match; no category name contains a hyphen.
- **Three taxonomy entries removed rather than special-cased.** bioRxiv `Epidemiology` and `Clinical Trials` and medRxiv `Vascular Medicine` are ignored by the API in every spelling tried, answering with the unfiltered listing. Advertising them as filters would return unrelated preprints under a filtered-looking request. `Epidemiology` stays medRxiv-only, so under `server="both"` it routes to medRxiv alone.
- **An ignored filter is checked on every response, not only at the taxonomy.** When a category was sent and `messages[0].category` echoes `"all"`, that leg's page is unfiltered. A single-leg call raises `invalid_category`; a `server="both"` fan-out drops the leg with a notice and fails only when no leg applied the filter. The leg is not added to `failed[]`: it answered, and retrying will not change the answer. When one leg failed and the other ignored the filter, the retryable upstream error wins, because the failed leg may still return a filtered page. An empty page carries no category echo, so it never trips the check.
- **`biorxiv_get_published_version` falls back to `/details`, then queries `/pubs` by journal DOI.** `/pubs/{server}/{doi}` never parses a `10.64898/` DOI. The preprint's `/details` record names its journal DOI, and `/pubs` keyed by that journal DOI returns the full crosswalk record, including journal name and date. The API reads only the first two `/`-separated segments of the key and answers a single-encoded `%2F` with a 404, but decodes the key once more itself, so a journal DOI with a second slash (`10.1093/genetics/…`, every Oxford University Press journal) has each slash after the first sent as `%252F` and resolves too — sent raw, those DOIs found nothing. When the reverse lookup still finds nothing, or fails, the journal DOI is returned alone with a notice, and `publishedJournal`/`publishedDate` stay absent rather than being inferred. Measured across 16 `10.64898/` DOIs: forward lookup 0/16, reverse lookup 14/16 with raw slashes, and both misses were multi-slash journal DOIs, the shape the double-encoded key resolves (checked live on four `10.1093/` journal DOIs). A crosswalk hit on the first lookup returns immediately, so the `10.1101/` path makes no extra calls.
- **A journal DOI resolves on `/pubs` alone, routed by prefix.** `/pubs/{server}/{doi}` is documented as keyed by either DOI, so a journal article's DOI returns the same record as its preprint's. Any DOI outside `10.1101/` and `10.64898/` is read as a journal DOI: the `/pubs` lookup across both servers is the whole call, and an empty answer everywhere is `doi_not_found` saying the crosswalk records no preprint for that article — `/details` never holds a journal DOI (it reads `10.9999/zzz` as a malformed date interval), so it is never asked. Routing by preprint-DOI *shape* instead was rejected: Cold Spring Harbor Laboratory Press registers its journal articles under `10.1101/` (`gr.…`, `gad.…`, `lm.…`), neither endpoint recognizes those keys, and the journal path's hint would deny a preprint that exists. They stay on the preprint path, whose not-found hint names the case instead of calling the DOI wrong.
- **One DOI normalizer for the three DOI-keyed tools.** `normalizeDoi` in `services/shared.ts` strips a `doi.org`/`dx.doi.org` URL, a `doi:` label, a `{www.}{biorxiv,medrxiv}.org/content/` URL (with its query and fragment), and a trailing `vN` plus any article-tab suffix (`.full`, `.full.pdf`, `.article-metrics`, `.supplementary-material`, …, matched case-insensitively), then requires `10.` + a 4+-digit registrant + `/` + a non-empty suffix. On a `10.1101/` or `10.64898/` DOI the suffix is anchored after a digit, so it only ever removes text around a bioRxiv/medRxiv identifier. Any other DOI is a journal's and loses only a trailing `/`, the page-format tabs (`.pdf`, `.full`, `.full.pdf`, `.full-text`, …), and a `vN` after a digit, read component by component from the end: a journal's component DOIs (`10.7554/eLife.55185.sa1`, `10.1371/journal.pone.0123456.g001`, Wiley's `….x`) end in a `.`-component of the DOI itself, and stripping it would resolve the parent record instead, while `10.1016/j.cell.2020.01.001.pdf` still names the article. A bare DOI that passed the old prefix check passes through unchanged. Results report the bare DOI; an unparseable entry is reported as sent.
- **`biorxiv_get_fulltext` takes a `version` input and honors a `vN` suffix; when both are given they must agree.** A pasted article URL names a version, and the versioned page is independently fetchable. Disagreement raises `version_conflict` before any API call, because picking either one would silently return text the caller did not ask for. A version the preprint lacks raises `version_not_found` listing the available ones. The next-chunk prompt carries `version=` so paging a non-latest version stays on it.

### Highwire placeholders, section headings, and Markdown escaping

- **The normalizer emits plain text, and `format()` escapes it.** `normalizeUpstreamText` runs at the service boundary so `structuredContent` and `content[]` carry the same text; it renders headings as `Heading: ` and list items as `• `, never as Markdown. Escaping happens in each `format()` at the point a field is interpolated, through the local `escapeMarkdown` (mcp-ts-core exports only `escapeHtml`). Escaping in the service would put backslashes into `structuredContent`, and escaping the assembled text would break the formatter's own `**Label:**` markup.
- **Placeholders map through closed tables; an unknown name stays verbatim.** `src/services/upstream-text-tables.ts` holds the brace names (`{beta}`, `{+/-}`, `{middle dot}`, …), the bracket forms (`[~]`, `[&ge;]`, `[-&gt;]`, `[isin]`, `TGF[beta]`, …), and `[xHHHH]` is read as a code point. The tables come from a sweep of 5,788 live `/details` records across 14 bioRxiv and medRxiv windows (2021-03 to 2026-09), with glyphs checked against EuropePMC's rendering of the same records — which is why `{epsilon}` is `ϵ`, `{o}` is `º`, and `[-]` is `―`. The Greek alphabet and superscript digits are filled out past what the sample held. A generic `\{[A-Za-z ]+\}` rule was rejected: it would rewrite LaTeX groups (`F_{e}`, `\mathrm{F}`), so braces after `_`, `^`, `\command`, or `{` are skipped and set notation like `{0, 1}` never matches a name.
- **Entities are decoded only inside their bracket placeholders.** Every `&gt;` in the sample sits inside `[-&gt;]`, which means `→`; decoding the entity alone would produce `[->]`.
- **The normalizer never assembles a tag the input did not hold.** `[xHHHH]` decodes only to a non-ASCII symbol — the sample's one code point is `[x1D05]` (`ᴅ`) — and any other code point stays verbatim, so `[x003C]iframe[x003E]` stays as sent. An inline tag is left in place when an open `<` precedes it with no `>` between, because removing `<i>` from `<scr<i>ipt>` would splice together a tag the input never held; the strip then repeats until nothing changes. Neither rule changes the output for any of the 5,788 sampled records.
- **Fused headings are split before whitespace collapses.** 1,162 of the 5,788 records fuse a section heading to its first word after a line break (`\n\nResultsInsulin-secreting …`), and the collapse that follows erases the only boundary. Paragraphs are split on the raw line breaks and matched against a closed heading list, longest first. A body led by a capital or digit splits; a lowercase-led token splits only when it carries a capital or digit (`ResultssDII`, `ConclusionsmiRNA`), since a plain lowercase letter is usually the heading word continuing (`Aimed`). A mixed-case match that ends in a capital has taken the body's first letter, so the shorter heading is tried instead: `AimSGLT2` is `Aim: SGLT2` and `ConclusionSARS-CoV-2` is `Conclusion: SARS-CoV-2`, never `AimS: GLT2`. `Aim` and `Aims` are never split before a digit, because they also open gene symbols (`AIM2`, mouse `Aim2`) and a fresh 1,982-record sample shows them fused only to words and acronyms (`AimTo`, `AimsSCORE2`). Single-line text is never split, which protects titles such as `DesignMaster: …`. EuropePMC marks the same headings up as `<h4>…</h4>` in `core` abstracts; those render as `Heading: ` too, so a fallback abstract reads like an enriched one.
- **A literal backslash-`n` is a line break, and a literal backslash-`"` a double quote, in text with no real line break.** Abstracts posted on bioRxiv before December 2019 write their breaks as the two characters `\` `n`, so the heading split above never fired on them (`…cases.\n\nResultsOver-expression`). A 976-record survey of `/details` listings (bioRxiv 2014–2026, medRxiv 2019–2026), with 227 earlier records, found the form in 119 records, all bioRxiv abstracts with numeric DOIs, none with a real newline, in titles, or on medRxiv: runs of two (232), one (30, between `C_LIO_LI` list items and inside figure blocks), and four (1), never `\r`. Every backslash in those records was `\n` (498) or `\"` (106); the escaped quote reaches body text in older abstracts (`we call \"type 1\"` in `10.1101/113506`), so it is read as `"` under the same conditions. No TeX command appeared, but LaTeX does reach upstream text, so a backslash opening a TeX control word that begins with `n` (`\nabla`, `\neq`, `\nu`; a closed list beside the placeholder tables) or following another backslash stays as written. TeX's `\"` umlaut accent (`\"o`) would lose its backslash too; none appeared in the sample. Text that already carries a real line break is read as before, byte for byte.
- **Tables and display figures are removed whole; text boxes and display formulas keep their text.** `O_TBL … C_TBL` follows the existing `O_FIG … C_FIG` precedent, caption included. `O_FIG_DISPLAY_L … C_FIG_DISPLAY` is matched before plain figures, because the lazy figure match stopped at the `C_FIG` inside `C_FIG_DISPLAY` and left `_DISPLAY` behind. Before the change, 1,953 of the 5,788 records (33.7%) carried at least one of these artifacts; after it, the only residue is one heading that does not open its paragraph (`(1) BackgroundMany …`).
- **The escape set is ``\ * _ ` ~ [ <`` plus line-initial `>`, heading `#` runs, and list markers, each escaped only where it can open syntax.** A line-initial `#` run counts only when a space, tab, or line end follows it, since only that opens a heading — so an award number such as `#441914366` stays as sent. Rendering the sample's `format()` output through markdown-it (CommonMark) and marked (GFM) found emphasis, code spans, a link, raw HTML, strikethrough, and ordered lists created by upstream text, and nothing else. Agents read `content[]` as text and copy spans into citations, so an escape that changes nothing is a cost. `\`, `` ` ``, and `*` are always escaped (`*` flanks emphasis intraword). `_` is escaped unless it sits between two letters or digits, where it cannot flank emphasis (`cc_by`, `snake_case`). `~` is escaped unless blank on both sides: marked strikes through a pair of *single* tildes, and consecutive `**Label:**` lines form one paragraph, so a lone tilde can pair with one in the next field. `<` is escaped only before a letter, `/`, `!`, or `?` with a `>` later — the shape of raw HTML or an autolink — so `p<0.05` and `x<y` stay raw while `IL-1<beta>`, which both renderers swallow as a tag, is escaped. `[` is escaped only before a later `](` or `][`, or opening a line a `]:` definition could follow. Escaping every occurrence put 12,021 backslashes into the sample's fields, 10,355 of them for the `_` in `cc_by`-style licenses; the narrowed rules put 261. Every escaped field in the sample renders back to its exact source text in both renderers. An apostrophe is not escaped (`NIH Director's` stays as sent), and neither are DOIs, `jatsxmlUrl`, `sourceUrl`, or `biorxiv_get_fulltext`'s extracted `content`, which agents copy back into calls or which is meant to render as Markdown.

### Funder metadata: awards only, and a funder filter on the listing

- **Records carry `awards`, not a funder name.** The three record tools used to render the `;`-joined `name` values of the upstream funder array as `funder`. Those names and their ROR IDs are misattributed: across 523 funder entries in the August 2026 bioRxiv listing, the most frequent name is an Amsterdam hospital carrying NIH-style awards, and none of the records returned by nine funder filters carries the filtered funder's ID. The award numbers do match the real funder, so each record now carries `awards: string[]` — the non-empty `award` values, trimmed, deduplicated in upstream order, never split — and no name or ID. `"N/A"`/`"NA"` award values are read as absent, like `published: "NA"`. `funder: "NA"`, no funder array, or no usable award leaves the field off. EuropePMC-fallback search records have no funder data and are unchanged. Removing `funder` is a deliberate output-contract change.
- **`awards` renders as one `**Awards:**` line, joined with `; ` and escaped as one field.** Escaping the joined string, not each award, keeps link detection across award boundaries honest and escapes a leading `#` only once.
- **The funder filter takes a ROR ID, normalized and checksum-checked before the call.** The API accepts only the bare 9-character form, so `https://ror.org/…` (any case, trailing slash) is stripped and lowercased, then checked against `0` + six Crockford base32 characters + an ISO 7064 Mod 97-10 checksum. A mistyped ID fails locally as `invalid_funder` without a request. A checksum-valid ID can still be unknown upstream, so the upstream status check stays.
- **Funder filtering is bioRxiv-only.** 240 of 240 August 2026 medRxiv records have `funder: "NA"`, and medRxiv answers any funder with `"no posts found"`. `server="both"` + `funder` queries bioRxiv alone, with a composed notice explaining the missing medRxiv entry, as a server-exclusive category does; `server="medrxiv"` + `funder` raises `invalid_funder`. A category is then validated against bioRxiv's taxonomy.
- **`"funder value not found"` raises `invalid_funder`, never an empty page.** The API answers it with HTTP 200 and no collection, which the listing parser would read as `total: 0`. `BiorxivApiService` flags it as `funderNotFound`, like `categoryIgnored`, and the tool throws. `"no posts found"` for a known funder is a real empty page, and the zero-result notice names the funder among the applied filters. One reason covers malformed IDs, `medrxiv`, and not-found: from the caller's seat each means "this funder value will not filter", and the per-site recovery hint says which fix applies.
- **The ignored-category guard still applies under a funder filter.** A funder-only page echoes `category: "all"`, but the guard fires only when a category was sent. With both sent, the API echoes the applied category, or `"all"` beside the funder echo when it ignored the category, which still raises `invalid_category`.
- **Structured `funders[]` output and name-to-ROR resolution are out of scope.** A record's own ROR ID fed back as `funder` draws `"funder value not found"`, so it cannot seed the filter, and ROR's own API resolves names.

### Journal publications by date: `biorxiv_list_published_versions`

- **A dedicated list tool, not a mode on `biorxiv_get_published_version`.** The crosswalk tool takes one DOI, returns one record, and fails `doi_not_found`; a paged list takes a date pair and returns an empty success with a notice, per-server `pagination`, and `failed[]`. One flat output object for both would leave every field optional. The list follows `biorxiv_list_recent`'s contract — the date pair and its `date_from`/`date_to` aliases, server fan-out, one input cursor with per-server state, `include_abstract` — so a caller who knows one listing knows the other.
- **Dates are validated locally.** The API answers an inverted range, a malformed date, and an empty interval with HTTP 200 and an empty page, so none of them may reach it: each would read as "nothing was published". The `YYYY-MM-DD` shape is in the input schema, as on `biorxiv_search_preprints`, so `tools/list` advertises the pattern and a malformed bound is `-32602` naming the field; both bounds are required, so a blank one is malformed, never unset. The calendar and order checks stay in the handler as `invalid_date_range`.
- **The cursor advances by upstream rows.** The service drops a row naming no preprint, so a page can hold fewer publications than the API returned. `rowCount` carries the API's count, and `nextCursor`, `exhausted`, and the empty-interval notice all read it, so a dropped row neither repeats a row on the next page nor reads as the end.
- **A local `limit`, default 25 rows per server.** A 100-row page per server made a `"both"` first page 258 KB with abstracts off, over the 50,000 characters at which Claude Code moves a tool result into a file, on both surfaces; no field dominated (authors 24%, title 19%), so trimming fields was no lever. The API takes no size parameter, so the service slices the upstream page before normalizing, and `rowCount` stays a count of upstream rows served. 25 is the largest round size whose `"both"` first page stays under that threshold and Claude Code's 10,000-token warning on each surface (65,660 B, about 31–34 K characters a surface), and it matches `biorxiv_search_preprints`' default. Above 100 the call serves the whole page with a notice, since a read past its per-call cap serves up to the cap; 1000 is the schema ceiling against confused input. Caching aligned upstream pages to avoid the repeat fetches a small-`limit` walk costs was not taken: walks are the minority case, and `limit: 100` restores the old cost.
- **`total` is absent only on an exhausted entry.** Upstream sends no total past the last row, unlike `/details`' `total: 0`; leaving it out keeps the response from claiming a count it never received. At cursor 0 an empty page is an empty interval, so the entry reports `total: 0`.
- **`include_abstract` defaults to `false`.** Abstracts were 71.9% of a 234 KB bioRxiv page, the same triage reasoning as `biorxiv_list_recent`.
- **The two server legs share the call's 50 s budget.** A page is about a quarter megabyte and the legs run in parallel, so the call settles inside a client's 60 s request timeout even when the origin hangs; a caller's cancellation is rethrown rather than reported as a partial page with one server in `failed[]`.
- **`publisher` reads `/publisher`, not a filtered `/pubs` page.** Its rows for a DOI prefix are exactly the bioRxiv `/pubs` rows with that `published_doi` prefix, and it pages the same way, so `cursor`, `limit`, `nextCursor`, `total`, and `exhausted` keep their meaning. Filtering a `/pubs` page locally was rejected: its totals and cursors would stop matching the rows returned, and a sparse publisher would take many empty pages. The service takes the listing's source as a server or `{ publisher }`, so a medRxiv publisher listing is unrepresentable below the tool.
- **`publisher` follows `funder` on `biorxiv_list_recent`.** The endpoint is bioRxiv's alone, so `"both"` narrows to bioRxiv with a notice explaining the missing medRxiv entry, and `"medrxiv"` is `invalid_publisher` before any request rather than an empty page. The schema pattern `^10\.\d{4,}$` takes the prefix alone, and the API's own format rejection (`"publisher string not recognized"`, HTTP 200, no rows) is `invalid_publisher`, never an empty page. A blank or whitespace-only value reads as omitted.
- **A `/publisher` row keeps its gaps.** It carries six keys, so `publishedJournal`, the author fields, and the abstract stay absent, even under `include_abstract: true`, rather than being filled from another source; a notice on both surfaces names the missing fields and routes to `biorxiv_get_published_version` for a full record.

### Abstracts: `include_abstract`, and fallback abstracts from EuropePMC `core`

- **`include_abstract` removes the abstract and nothing else.** Abstracts are about three quarters of a listing page (74.7% of a two-server page's `structuredContent`) and 70% of a search page. Truncating them leaves a partial abstract with no way to get the rest, and dropping more fields (JATS URL, license, type, corresponding author) takes a two-server page only from 79 KB to 46 KB while losing metadata a listing is read for. `awards` and every other field stay, on both surfaces.
- **`biorxiv_list_recent` defaults to `false`; `biorxiv_search_preprints` to `true`.** A listing is triage — titles and categories first, then a few DOIs — and its page size is fixed by the API, so the caller had no other way to ask for less. Ranked search hits are usually read in full, and `limit` already bounds them. The listing default is a deliberate output-contract change: a caller reading `abstract` from a listing passes `include_abstract: true`. The field was already optional in the output schema, so the advertised schema is unchanged. `biorxiv_get_preprint` (up to 10 DOIs) is the follow-up for a few abstracts; at 10 DOIs a call, the listing flag is cheaper for a whole page.
- **The abstract is the preprint's, so it sits on the latest revision only.** `/details` repeats the latest revision's abstract on every revision while title, authors, and date stay per-revision: 22 multi-revision preprints (15 bioRxiv, 7 medRxiv, first posted 2016–2025; 65 revisions) each carried one abstract across all revisions, and the v1 article pages of `10.1101/049882` and `10.1101/2024.02.20.581273` show a different one. `getDetails()` returns revisions sorted ascending by version number (stable; a row with no number sorts first) and keeps it on the last, so `biorxiv_get_preprint`, search enrichment, and `biorxiv_get_published_version` all read the same latest revision whatever order upstream lists them in, and `biorxiv_get_preprint` no longer shows an earlier revision an abstract it never had; the field was already optional, so the schema is unchanged. An earlier revision's own abstract is on its versioned article page (`biorxiv_get_fulltext` with `version`); medRxiv answers HTTP 403 for its article pages to some hosts, which that tool reports as `fulltext_unavailable`. A listing row keeps its abstract and `.describe()` calls it the latest-revision abstract: no row names the latest version, and spotting a superseded row costs a `/details` call per row (30–60 a page), while dropping abstracts from `version > 1` rows would be wrong both ways — v1 rows can be superseded and 9 of 13 sampled v2+ rows were the latest.
- **The ranked search stays `lite`; fallback abstracts come from one `core` query.** EuropePMC ignores `fields` and never includes `abstractText` in `lite` results, so records that fell back to EuropePMC metadata had no abstract at all. Switching the ranked search to `core` would make every search pay about five times the transfer for records that enrichment then replaces. Instead, when abstracts are requested and any record fell back, `EuropePmcService.getAbstracts` sends one `(DOI:"…" OR …) AND SRC:PPR` query at `resultType=core` with `pageSize` equal to the number of fallback DOIs. A fully enriched search, or one with `include_abstract: false`, makes no `core` request.
- **A failed abstract lookup degrades like enrichment.** The fallback records come back without an abstract, and a notice says how many and whether EuropePMC rate-limited the lookup (naming the wait) or it failed, so a retry is the next step. The notice is composed with any other qualification because `ctx.enrich.notice` is last-wins. A DOI EuropePMC holds no abstract for is simply absent, with no notice.

### Blank date bounds, and a zero `Retry-After`

- **A blank `date_from` / `date_to` on `biorxiv_search_preprints` is unset, and the `YYYY-MM-DD` shape lives in the schema.** Form clients send every displayed optional field as `""`. The handler's truthiness checks let a blank through to `EuropePmcService.search`, which fills only a nullish bound, so EuropePMC got an open `FIRST_PDATE:[2026-09-01 TO ]` clause: a blank `date_to` dropped the filter (586 hits against 14), and the echo claimed it applied. A `blankAsUnset` preprocess maps `""` to `undefined` before a `regex` validator, so `tools/list` advertises the pattern and a malformed shape is `-32602` at the schema. The calendar check (`2024-02-30`) and the order check stay in the handler as `invalid_date_range`, since a pattern cannot express either. `EuropePmcService.search` also reads a blank bound as absent, so no caller can build the open clause. `biorxiv_list_recent`'s dates are required, so the blank rule does not reach them; they carry the same `regex` (with no `blankAsUnset`), so its handler keeps only the calendar and order checks, and its `date_from` / `date_to` aliases land on the patterned fields.
- **Record `server` is the queried server, lowercase.** `/details` spells it `"bioRxiv"` / `"medRxiv"`, which every tool's case-sensitive `server` input rejects, while every other server-valued output field was already lowercase from the queried leg. All 254 `/details` records sampled matched the server queried, so setting the field from that server loses nothing and lets it be typed `z.enum(['biorxiv', 'medrxiv'])` — always present on `biorxiv_get_preprint` and `biorxiv_list_recent`, on enriched records of `biorxiv_search_preprints`. Accepting either case on input was declined: it would leave two spellings of one value in outputs for one producer's quirk.
- **A `Retry-After` of `0` or a past HTTP-date is no usable wait.** `parseRetryAfterSeconds` returns `undefined` for it, so every caller takes its existing no-header path: generic wording, no `retryAfter`, since "wait 0 seconds" would send the caller straight back into the limiter. The retry ladder reads it the same way. `withRetry` takes a zero wait as a wait to honor and re-sends at once, four requests within milliseconds into the limiter that just refused, so `retryWithinBudget` hands it each such 429 without the header (the origin's error rides along as `cause`). The ladder then backs off exponentially inside the call's one deadline, the same requests and waits as a 429 with no header, on every origin. A backoff that would outlast the deadline still ends with that 429, classified `rate_limited`, never an expiry. A positive `Retry-After` reaches `withRetry` untouched.

### `biorxiv_search_preprints`: a `limit` above 100

- **Above 100 the search serves 100, never a rejection.** It is a read with a continuation (`nextCursorMark`), so serving the first 100 costs the caller nothing, while a `-32602` cost a round trip. 100 stays the per-call cap because it also bounds the enrichment fan-out and the abstract lookup; 1000 is the schema ceiling against confused input. A clamped call says so in the notice, and sets `truncated`/`shown`/`cap` only when the page holds all 100, since a shorter page was not cut.
- **`queryEcho.limit` echoes the value sent, 100.** The echo exists to show what produced the result set, so echoing the requested 250 would claim a page size EuropePMC never got; the notice names the requested value. A second echo field for one edge case was not worth the schema surface.

### Full text: citation labels, references, and omitted tables

- **The article page is reshaped before extraction, not the extractor's rules.** Defuddle strips every `a[href^="#"]` whose class contains `ref` — every `a.xref-bibr` / `a.xref-fig` / `a.xref-table` label, leaving `()` behind — renumbers numeric citations through its footnote pass (`[^1]–[^3]` for `(1–16)`), and removes each reference's `div.cit-metadata` with its `metadata` partial selector. The framework `htmlExtractor` exposes none of those switches, and disabling them would re-admit the page chrome they strip, so `BiorxivFullTextService` parses the page with `linkedom` first: each cross-reference anchor becomes its own text, the reference list loses its `↵` backlinks and every `class`/`id`, and the page goes to the extractor serialized. On three captured articles every reference survives (72/72, 30/30, 27/27, from 0, 1, and 0) and every label with no `()` or `[^` left. The extra parse and serialize costs about 6–8 ms on a 240–350 KB page, and the end-to-end extraction is no slower, since Defuddle has fewer anchors and link-outs to process.
- **Reference link-outs: the DOI only, as a `doi.org` link.** Each entry's `.cit-extra` carries OpenURL links built from an unexpanded `{openurl}` template, PubMed links whose `access_num` is often truncated (`http://www.n`), and Web of Science and in-journal links. Only the CrossRef DOI link is kept, rewritten to `https://doi.org/<doi>` with the DOI as its text so a caller can copy it. Each entry shows one number, the one the page prints (see *Full text: figures, display formulas, and reference numbers*).
- **Tables are named, not fetched.** A Highwire article page carries no table cells, only each table's caption and a link to an expansion page on the same origin. Fetching them would cost one request per table against an origin that rate-limits after a handful of page fetches. Every table's callout links go, cells or not; the caption stays in place, and `omittedTables` (`label`, `url` of the popup page; the table's `id` stands in for a label the page does not print) rides in the cached article, so it appears on every chunk, in `structuredContent` and as a list in `content[]`. The list is structured output rather than a note inside the extracted text, where the extractor would escape bracketed prose. A `div.table` that does hold a `<table>` is not listed.
- **The cache key moved to `fulltext/v3`.** The cached article gained `omittedTables` and changed its text, so entries written under `v2` are never read back.
- **`limit` has no ceiling.** It is a character budget for one chunk, and the extracted text already bounds it: a value past the remaining text returns the rest with `hasMore: false`. The old `.max(50000)` only cost a caller who wanted the whole article in one call a failed round trip.

### Full text: figures, display formulas, and reference numbers

- **Each figure renders as its image, labelled, then its caption once — by reshaping the figure's markup, never by deleting Markdown text.** A Highwire figure's image link carries the caption in its `title` and the image carries it again in its `alt`. Defuddle emitted the alt as the image text and again as a paragraph, and its empty-link cleanup (a regex that stops at the title's first `)`) left the rest of the title, HTML-escaped and ending `")`, spliced onto the preceding paragraph, caption, or heading; a title with no `)` glued the image onto the preceding line instead. On 11 captured articles (101 figures) that was 84 spliced lines, 66 of them body prose. Each `div.fig` now loses its "Download figure" / "Open in new tab" list, and each `.fig-inline-img` is replaced by a bare `<img>` (src from `data-src`, or a `src` that is not a `data:` placeholder) in its own paragraph, alt-texted with the printed label without trailing punctuation. The `div.fig-caption` stays as the caption, since it alone keeps the label, sub/superscripts, and italics, and the alt and title were truncated copies in 17 figures. A figure holding several images numbers them (`Fig. S16 (1 of 2)`): Defuddle collapses adjacent images that share an alt. A text-level fix was rejected because by then the residue is merged into real paragraphs.
- **Each display formula is an image block of its own, between the intact text around it.** The page sets a formula's image (`span.disp-formula`) inside its sentence's paragraph with the alt `Embedded Image`. Defuddle takes an alt of ten or more characters on an image inside a `span` for a caption, so it built a captioned figure, and the figure's start tag closed the open paragraph: every formula added an `Embedded Image` paragraph (16 of 16 on four captured articles), and a formula that followed text after an earlier formula in the same paragraph was glued onto that text (3 of the 16). Each formula is now a bare `<img>` in its own paragraph, and a paragraph that held formulas is split around them in one pass over its children, dropping the whitespace-only runs. The alt is empty: the page prints no formula label to use, and Defuddle collapses adjacent images that share a non-empty alt, which loses one of two equations set in consecutive paragraphs.
- **Each inline formula stays inside its sentence, as an image with an empty alt.** The page gives an inline formula's image (`span.inline-formula`) the same `Embedded Image` alt, so Defuddle lifted it out of the sentence into a captioned figure: the alt became a paragraph of its own and the sentence's tail started a new one. Each inline formula span is now a bare `<img>` where it stood, with an empty alt, and renders as `![](…)` mid-sentence.
- **A reference list numbers each entry once.** Every captured list (594 entries in 12 lists) printed the list ordinal and the entry's own label (`1. 1.`, `1. (1).`, `1. \[1\].`, and `1. 53.` for a Methods list labelled from 53). When an `ol.cit-list`'s labels are consecutive integers, the list gets `start` at the first label and the label spans go; any other list keeps its labels and renders unordered, so a list that skips entries still matches an inline `16` to its entry by its printed label.
- **Every reshaping pass runs in linear time.** Each pass that queries a subtree — cross-reference anchors, inline and display formulas, figures and their image holders, reference lists and their link-out blocks, tables — runs over the outermost matches only, whose subtrees are disjoint; a match nested inside another is handled as part of it.
- **The cache key generation moves with every change to this reshaping (now `fulltext/v5`),** so extractions rendered before a change are never read back.

### Full text: short sections and nested reference lists

- **Every block in the article container is marked as content.** Defuddle's low-score removal stops counting a block under 200 words as content when any of its headings contains a navigation word as a substring (`related`, `responses`, `share`, `terms`, …), then removes it when its whole-word indicators (−10 each) outweigh its commas: medRxiv 26365491's section `3.2 Effect of suppressing the vaccination-related input` (171 words, 4 commas) was dropped whole. `prepareArticlePage` sets `role="article"` on every block element the scorer reaches inside `.fulltext-view`, which `isLikelyContent` checks first. The framework extractor exposes no `removeLowScoring` switch, and a second direct Defuddle call would bypass its input budget and error classification. Blocks inside a table or `pre` stay unmarked: the scorer skips table cells and `pre`, and a marked block anywhere in a table, its caption included, stays a `<div>` in a table written as HTML. On every other captured fixture the scorer removed nothing inside the container, and each renders byte-identical with the marker.
- **A list nested in a reference entry is set inline, or dropped when it only repeats the entry.** An edited volume's editors marked up as an `<ol>` inside the entry rendered as numbered items ahead of the citation, or, within 500 characters of either end of the article text, were deleted by Defuddle's blog-metadata-list rule. Each nested list, and every list within it, gives way to its items' content in page order, with a space before each list and after each item; nothing is reordered, so the editors stay where the page puts them. Highwire also prints an `ol.duplicate` copy of editors the citation already names (bioRxiv 736286 v2, reference 7: `In A. Rich, and N. Davidson, editors`), which set inline would print them twice, the first time ahead of the authors. A nested list marked `duplicate` is dropped when it holds nothing but list items and the rest of the entry, read without any of its nested lists, names every item as whole words, in list order — the item's text with whitespace collapsed and its trailing separators (`,`, `;`, `&`, ` and`) trimmed; a name that is only the start of a longer one (`N. David` in `N. Davidson`) does not count. Any other nested list, or a duplicate one naming someone the rest of the entry does not, is set inline, so no text is lost. Matching in list order keeps the check linear: each search starts where the last match ended, where an unordered search per name costs the number of names times the entry's length.

### One time budget per tool call

- **One 50 s budget per tool call, not a deadline per ladder or fewer retries.** Chained ladders add up: four attempts of 15–30 s plus backoff already outlast the 60 s request timeout MCP SDK clients default to, and `biorxiv_search_preprints` runs three ladders back to back. A client that has given up never sees the classified error or the degraded result. Each handler calls `startCallDeadline()` once and passes the same `CallDeadline` to every service call, which runs each ladder through `retryWithinBudget`, handing `withRetry` what is left (`remainingBudgetMs`), and caps each attempt at its usual timeout or that remainder. A healthy origin sees the same attempts and results as before.
- **A 429 stays the origin's answer when the budget runs out.** `withRetry`'s expiry carries only the last attempt as its `cause`. When every attempt answered 429 slowly and the budget cut a later one off mid-request, the 429s were lost and the call reported an outage (`upstream_unavailable`, `search_unavailable`) where the full ladder had reported `rate_limited`. `retryWithinBudget` remembers the last 429 any attempt received and, on an expiry, rejects with it, `Retry-After` included, so the services classify it as they classify a 429 that exhausted the ladder. An expiry with no 429 behind it stays an expiry, and a caller cancellation stays a cancellation.
- **The deadline never aborts `ctx.signal`.** It bounds the ladder through `deadlineMs` and the attempt `signal`, so a caller's cancellation stays `RequestCancelled` and an expiry stays a `Timeout` the tool reports as its declared upstream reason.
- **Required steps fail, degradable steps degrade.** A search, a version resolution, a crosswalk, a listing, or an article page that runs out the budget fails with the tool's retryable `upstream_unavailable`, `search_unavailable`, or `rate_limited`. Enrichment, the fallback abstract lookup, and the crosswalk by journal DOI degrade as they do for any other failure: an enrichment falls back to EuropePMC metadata per record (`enrichment_error: service_error`), and the abstract lookup and the crosswalk by journal DOI say so in a notice.
- **A DOI lookup across both servers ends on the server that holds the DOI.** A preprint, its revisions, and its crosswalk record live on one server, so once one leg returns them no other leg's answer can change the result. Each DOI in `biorxiv_get_preprint`, `biorxiv_get_fulltext`'s version resolution, `biorxiv_get_published_version`'s crosswalk and `/details` steps, and `biorxiv_search_preprints` enrichment of a DOI with neither preprint prefix settle on that leg (`firstHit` in `services/shared.ts`) and abort the other one, rather than awaiting both: under `Promise.allSettled`, a stalled server that did not hold the DOI spent the whole budget — in `biorxiv_get_preprint` every DOI the other server had already found waited it out, and in `biorxiv_get_fulltext` the article page was then requested with none left, so the error blamed the page. Search enrichment of a `10.1101/` or `10.64898/` DOI stays sequential, bioRxiv then medRxiv only on an empty answer: it never waits on a server whose answer cannot matter, and running both at once would double its requests for every bioRxiv preprint. The crosswalk's server scoping was checked live: `/pubs/medrxiv/` keyed by a bioRxiv preprint's DOI answers an empty collection. `/details` is scoped the same way — keyed by a DOI the other server holds, it answered an empty collection for two bioRxiv preprints and one medRxiv preprint (checked 2026-10-17) — so taking the holding server's revisions alone drops nothing the merge of both answers carried. Each leg runs on its own signal combined with the caller's (`getDetails` and `getPublishedVersion` take it as an optional last argument, defaulting to `ctx.signal`), so a cancellation still reaches every leg and still settles as `RequestCancelled`. Only the legs that had answered when the step ended are read, for a rate limit or a failure.
- **`biorxiv_get_fulltext` requests the article page with whatever budget resolution left, and says when the lookup used it up.** There is no minimum page budget. With any budget left the page is requested, and with none a cached extraction is still served. The lookup is named instead of the page when the page fetch ended on the budget before the page itself failed (never requested, or its one request still waiting when the budget ran out) and resolution had used most of the budget. The `upstream_unavailable` then states how long the lookup took and how much the page got, names the lookups that did not answer, and sends the retry to the holding server, so the retry spends the whole budget there. A page that timed out on its own, answered an error, or had the larger share of the budget keeps its own failure and the `biorxiv_get_preprint` fallback.
